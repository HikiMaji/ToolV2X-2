## 必须修复

### 1. 单个代理组件不可估会连带关闭仍可拟合的直接对照

位置为`fit.py:120–128`、`fit.py:154–175`及`kernel.py:200–205`。

`fit_models`依次拟合全部组件，任一组件不可估就整体抛错，已经成功的D也无法返回。`predict_row`在预测D前就强制读取pi和T_base，后续还无条件读取全部状态模型。`score_window`则无条件先计算T/J，因此runner无法仅凭给D标可用来保留该对照。

具体情况是clean数据有合法报告0/1，但所有可用Z恰为1。直接D仍可估，h_B按规格应不可估。此时当前接口把D也一起丢失。类似地，条件转移不可估时，已经能估的B/C也不能独立评分。这个结果不符合SDS第5节“参数不可估方法标unestimable”的组件边界，也不能完成“代理不可估时保留简单D判断”的预定方法决定。把整批所有方法都标unestimable会把实现限制误写成全部模型的数据不足。

本次仅针对新疑点运行一个小fixture，未重复24项已通过测试。使用两父、每父12帧、合法0/1报告、Z全1的数据，实测结果如下。

```
D_standalone_estimable True
fit_models_error ValueError h_B not estimable: logistic not estimable: finite samples and both classes required
D_only_predict_error KeyError 'pi'
```

最小修法是按已有组件记录可估状态和错误，返回已成功参数，不伪造失败组件参数。沿固定依赖关系决定方法可用性，D只依赖D，B依赖h_B/emission，C依赖h_B/h_C/emission，T/J及两个消融再依赖所需转移/初始化组件和rho。公共假侧不依赖代理监督，应继续计算。预测和计分只运行可用方法，不可估方法保留同一record和共同分母、分数为None并明确unestimable原因。也可采用等价的简单分支实现，无需引入新框架。

该规则只用于明确的参数不可估。已经声明可用的模型发生数值异常时，继续遵守主会话确定的同record各方法共同unknown规则，不能把异常当作缺组件而悄悄绕过。OOF只依赖其需要的正常时序组件；它们不可估时J及依赖rho的消融应明确关闭，不能拿rho=0伪装成已估参数。

必要新增验收只覆盖两个分支。Z无类别变化但D可估时，D返回有限分数，代理方法为unestimable；转移不可估但静态组件可估时，静态对照继续评分。原来的数值异常共同unknown测试仍须成立。
