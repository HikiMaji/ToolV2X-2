# ToolV2X 硕士论文整体研究方案 v1

## 一、总体研究目标

面向 V2X 协同驾驶场景，研究车辆如何在有限通信与计算资源下，利用大模型智能体根据当前驾驶任务主动调用邻车私有能力，并根据真实调用结果和驾驶方案变化持续调整后续协作行为。

整体研究分为两个递进方向：

### 研究点一：有效协作
**基于多模态大模型智能体的 V2X 远端能力调用与反馈式协同驾驶方法。**

核心问题：

> 本车何时需要远端信息、应该调用哪类远端能力，以及获得真实远端信息后是否还需要继续协作？

### 研究点二：安全协作
**面向不可信协作节点的远端能力可信评估与安全驾驶决策方法。**

核心问题：

> 当合法协作车辆可能提供错误、异常甚至恶意的 P/F 结果时，本车如何检测、验证、拒绝或重新调用能力，避免协作信息误导驾驶决策？

两个研究点共享同一套 Agent、P/F capability、规划器、receipt/provenance 与评价平台。

---

# 二、研究点一：LLM Agent 驱动的 ToolV2X

## 2.1 核心思想

不再让大模型直接负责低层数值轨迹生成。

系统中将能力分为：

- **Local PLAN**：本车本地数值规划能力；
- **Remote P**：邻车私有因果感知/跟踪状态能力；
- **Remote F**：邻车基于完整私有上下文的运动预测能力；
- **LLM Agent**：负责判断是否需要远端协作、调用 P 还是 F、采用 current/change，以及何时停止。

因此：

> 大模型负责“怎样组织能力”，数值规划器负责“具体怎样开车”。

总体结构：

```text
                 LLM Agent
                    │
              P / F / STOP
                    │
       ┌────────────┴────────────┐
       │                         │
   Remote P                  Remote F
状态/历史能力              运动预测能力
       │                         │
       └──────── evidence ───────┘
                    │
             Evidence Adapter
                    │
               Local PLAN
                    │
                  trajectory
                    │
               LLM Agent
                    │
                 repeat
```

# 三、Agent Loop

## 3.1 初始阶段

首先利用本车已有的因果信息和导航任务进行一次本地规划：

\[
(O_t^{local},H_t,R_t)
\xrightarrow{PLAN}
\tau_0
\]

其中：

- \(O_t^{local}\)：当前本车局部感知；
- \(H_t\)：本车及交通参与者历史信息；
- \(R_t\)：导航/路线任务；
- \(\tau_0\)：未使用新远端信息生成的初始驾驶方案。

**初始 PLAN 必须执行。**

LLM 不负责决定“要不要先规划”。

原因是远端信息价值应当相对于当前驾驶方案定义，而不能仅根据“场景是否复杂”判断。

---

## 3.2 第一次 Agent 决策

生成初始方案后，构造 LLM 状态：

\[
S_0=
\{
G_t,
X_t^{ego},
O_t^{local},
\tau_0,
B_0
\}
\]

其中：

- \(G_t\)：当前 navigation / driving goal；
- \(X_t^{ego}\)：速度、yaw rate、历史运动等；
- \(O_t^{local}\)：本车当前可获得的场景摘要；
- \(\tau_0\)：当前数值规划方案及其结构化摘要；
- \(B_0\)：剩余远端调用次数、通信预算、计算预算。

第一次允许的 Agent 动作为：

\[
a_1\in
\{
P_{\text{current}},
F_{\text{current}},
STOP
\}
\]

含义分别为：

- `P-current`：请求与当前方案相关的远端状态/历史信息；
- `F-current`：请求与当前方案相关的远端预测信息；
- `STOP`：认为本地信息已经足够，不进行协作。

第一次必须允许 STOP。

否则 Agent 无法真正学习“何时不需要通信”。

---

# 四、P/F 调用语义

## 4.1 P capability

P 不简单定义成“发所有检测结果”。

其语义为：

> 利用 peer 的私有因果 tracking state，针对当前驾驶任务检索最相关的状态与历史信息。

LLM 首版只决定：

```text
P-current
P-change
```

具体返回哪些目标，由 provider 根据当前 plan、私有上下文、budget 和已有 receipt 进行 task-conditioned ranking。

这样避免让 LLM 自由生成：

- track id；
- ROI；
- 任意 horizon；
- 不存在的目标。

---

## 4.2 F capability

F 定义为：

> peer 利用完整合法私有上下文及冻结预测模型产生运动预测，并根据当前驾驶任务选择值得返回的预测结果。

同样，首版 LLM 只负责：

```text
F-current
F-change
```

具体 target 由 provider 侧决定。

因此 LLM 学习的是：

> “当前更缺状态信息还是未来行为信息？”

而不是学习底层检索 API 参数生成。

---

# 五、第一次调用后的反馈闭环

假设 Agent 选择：

\[
a_1=P
\]

peer 返回真实证据：

\[
E_1
\]

系统必须自动重新运行规划器：

\[
PLAN(O,H,R,E_1,\tau_0)
\rightarrow
\tau_1
\]

这一步不是 LLM 自由决定是否执行，而是 Agent 环境的强制 transition。

因此保证：

\[
E_1
\rightarrow
\tau_1
\rightarrow
Q_2
\]

始终成立。

---

# 六、第二次 Agent 判断

第二次判断与第一次存在本质区别。

第二次 Agent 输入应包含：

\[
S_1=
\{
G,
X^{ego},
O^{local},
\tau_0,
E_1,
\tau_1,
\Delta\tau_1,
M_1,
B_1
\}
\]

其中新增：

### 1. 第一次方案 \(\tau_0\)

调用远程能力之前准备如何驾驶。

### 2. 已获得证据 \(E_1\)

第一次 P/F 实际获得了什么。

### 3. 新方案 \(\tau_1\)

使用真实 evidence 后如何重新规划。

### 4. 方案变化

\[
\Delta\tau_1=\tau_1-\tau_0
\]

除了数值轨迹，也可提供确定性摘要，例如：

```text
maneuver:
lane_keep → merge_right

lateral_change:
1.4 m

speed_change:
-2.1 m/s

critical_entity:
obj_7 → obj_13
```

### 5. Tool memory \(M_1\)

包括：

- 已调用 P/F；
- receipt；
- 已取得字段；
- provenance；
- 已花费 communication/compute。

### 6. 剩余预算 \(B_1\)

例如：

```text
remaining remote calls = 1
remaining bytes = ...
```

---

## 第二次动作空间

如果 \(\tau_1\neq\tau_0\)，可允许：

\[
a_2\in
\{
P_{\text{current}},
F_{\text{current}},
P_{\text{change}},
F_{\text{change}},
STOP
\}
\]

最多两次远端调用。

若发生第二次调用：

\[
E_2\rightarrow PLAN\rightarrow\tau_2
\]

之后结束当前 episode。

---

# 七、LLM 与 Planner 的输入必须区分

## Planner

负责连续空间驾驶，输入完整数值信息：

\[
Z_t=
\{
scene\ features,
ego\ history,
navigation,
local\ entities,
P,
F,
previous\ plan
\}
\]

输出：

\[
Z_t\rightarrow\tau_t
\]

---

## LLM Agent

不建议直接输入完整高维 tensor。

应输入可追溯的结构化 Agent state：

```text
NAVIGATION
local_goal = [...]

EGO
speed = ...
yaw_rate = ...

LOCAL OBJECTS
obj_1:
  position = ...
  velocity = ...
  history_valid = ...

LOCAL COVERAGE
...

CURRENT PLAN
waypoints = [...]
maneuver = ...
closest_object = ...
min_clearance = ...

ACQUIRED REMOTE EVIDENCE
...

PREVIOUS PLAN
...

PLAN REVISION
...

BUDGET
...
```

重要原则：

> Agent state 中的信息必须能够从 causal state、planner output 和已购买 evidence 确定性重建。

不要引入另一个隐藏的“专家摘要器”，提前告诉 LLM：

```text
risk = high
need F
```

否则真实决策责任会变得模糊。

---

# 八、最重要的因果约束：peer-private information 默认不可见

定义真实状态：

\[
X=
\{
X_{ego},
X_{local},
X_{peer-private}
\}
\]

但 LLM 在线只能看到：

\[
O_t=
\{
X_{ego},
O_{local},
R,
\tau_t,
E_{acquired}
\}
\]

其中：

\[
X_{peer-private}\notin O_t
\]

除非通过合法 P/F 调用得到。

因此必须建立明确的 **LLM visibility whitelist**：

LLM 可以看到：

- ego causal state；
- local sensing；
- navigation；
- current/previous plan；
- 已取得 P/F evidence；
- receipt；
- budget。

LLM 不能看到：

- 未购买的 peer objects；
- 未调用的 peer forecast；
- provider 完整上下文；
- future GT；
- 候选 Tool 调用后的未来结果。

这是 ToolV2X 成立的基本前提。

---

# 九、问题形式化

ToolV2X 可形式化为：

> **部分可观测环境下，具有通信与计算成本的 peer-private driving evidence 主动获取问题。**

Agent 策略为：

\[
\pi_{\theta}(a_t\mid S_t)
\]

其中：

\[
a_t\in
\{
P,
F,
STOP
\}
\]

或反馈阶段进一步包含 current/change。

核心不是：

> “LLM 会调用工具。”

而是：

> **LLM 根据当前驾驶方案和已经获得的真实信息，在有限资源下主动获取尚不可见的 peer-private driving evidence。**

---

# 十、ToolV2X Agent 数据集

暂称：

> **ToolV2X-Instruct / ToolV2X-Agent**

一条数据不是普通 QA，而是一条 Agent trajectory。

例如：

```text
[STATE]
ego state
local perception/history
navigation
budget

[TOOL]
PLAN

[RESULT]
τ0

[AGENT]
P-current

[TOOL RESULT]
E1

[TOOL]
PLAN

[RESULT]
τ1

[AGENT]
F-change

[TOOL RESULT]
E2

[TOOL]
PLAN

[RESULT]
τ2

[AGENT]
STOP
```

用于训练 LLM：

- 是否调用；
- 调 P 还是 F；
- current/change；
- 何时 STOP。

轨迹数值预测仍由独立 PLAN 模型训练。

---

# 十一、Tool 标签不能主要靠人工或 GPT 生成

Tool policy 的训练标签最好来自**离线反事实展开**。

## 初始状态

对同一 \(S_0\)，离线执行：

\[
STOP,\quad P,\quad F
\]

得到不同最终 planning outcome。

利用只在训练数据生成阶段可访问的 future label 计算：

\[
U(a)=
-\mathcal L_{\text{drive}}(a)
-\lambda C_{\text{comm}}(a)
-\mu C_{\text{compute}}(a)
\]

得到：

\[
a^*
=
\arg\max_a U(a)
\]

作为 Tool SFT 标签。

future GT 可以用于**离线 teacher label**，但绝不能成为在线 Agent 输入。

---

# 十二、STOP 的监督

如果远端调用只产生极小改善：

\[
U(P)-U(STOP)<\epsilon
\]

或：

\[
U(F)-U(STOP)<\epsilon
\]

则标注：

\[
STOP
\]

而不是强制通信。

因此数据集中必须有充分的：

- no-tool；
- P；
- F；
- P→F；
- F→P；
- first-call then STOP；
- feedback causes second-tool change

样本。

否则模型非常容易退化成“有 Tool 就总调用”。

---

# 十三、第二阶段 Tool label 的生成

必须固定同一个实际第一轮 prefix。

例如：

\[
\tau_0
\rightarrow P
\rightarrow E_1
\rightarrow\tau_1
\]

然后在同一个：

- \(\tau_0\)
- \(E_1\)
- receipt
- \(\tau_1\)
- remaining budget

下比较：

\[
STOP,\;
P_{\rm current},\;
F_{\rm current},\;
P_{\rm change},\;
F_{\rm change}
\]

得到第二阶段 teacher action。

这样才能真正训练：

> “获得第一次信息以后该怎么办？”

而不是混合不同第一轮历史。

---

# 十四、训练路线

## Stage 0：Oracle feasibility

训练 LLM 前先计算离线 oracle。

首先回答：

> 如果有完美 Tool policy，动态调用是否真的比固定 P/F/PF 更好？

如果 oracle 本身没有明显收益，则不能指望 LLM 训练解决问题。

必须先统计：

- oracle STOP rate；
- oracle P/F 比例；
- 第二次调用比例；
- feedback 后 action 改变比例；
- oracle 相对 fixed policy 的质量—成本优势。

---

## Stage 1：Prompt-only baseline

先测试 pretrained LLM/MLLM zero-shot 或 few-shot Tool calling。

---

## Stage 2：SFT

用 ToolV2X-Agent 数据做 instruction tuning。

主要训练：

\[
S_t\rightarrow a_t
\]

而不是轨迹生成。

---

## Stage 3：可选策略优化

若 SFT 已有效，再考虑：

- preference optimization；
- DPO；
- GRPO；
- offline RL。

开题阶段不必承诺一定采用 RL。

---

# 十五、为什么需要 LLM：必须通过实验回答

需要设置：

1. heuristic policy；
2. MLP policy；
3. small Transformer policy；
4. prompt-only LLM；
5. SFT LLM；
6. offline oracle。

比较：

- Tool action accuracy；
- driving quality；
- communication；
- computation；
- STOP accuracy；
- multi-step decision quality。

如果简单 MLP 已经与 LLM 相当，应收缩大模型贡献，而不能为了使用 LLM 人为复杂化问题。

LLM 更合理的潜在优势应来自：

- heterogeneous capability semantics；
- navigation/task language；
- 多实体关系；
- plan revision；
- 多轮 tool memory；
- 后续可信性/安全信息融合。

---

# 十六、可靠 PLAN backbone

这是研究点一成立的重要基础。

当前自建 structured driver 可以继续保留为：

- lightweight planner；
- diagnostic planner；
- ablation planner。

但主实验应优先建立一个有可靠方法来源、完整任务输入、合理监督和实际驾驶能力验证的 cooperative-driving planner。

原则是：

> 先证明 PLAN 能有效规划，再研究 Tool policy。

不能再次使用：

> “P/F 有梯度”

代替：

> “P/F 能帮助驾驶”。

---

# 十七、实时系统边界

LLM 不应该等同于高频控制器。

建议区分：

## High-rate

Numerical planner 持续运行。

## Low-rate / event-driven

LLM Agent 在：

- 新决策 epoch；
- 新远端返回；
- 明显 plan revision；
- 特定协作触发条件

下执行 Tool decision。

研究阶段仍可采用固定物理时刻最多两次远端调用。

最终报告应分别统计：

- LLM inference latency；
- planner latency；
- P/F provider latency；
- communication bytes；
- primitive calls；
- RPC rounds。

没有实测之前不宣称 real-time。

---

# 十八、研究点一核心实验

统一 backbone、统一数据、统一 budget 比较：

### 固定策略

- Ego / STOP
- fixed P
- fixed F
- fixed PF
- fixed P→F
- fixed F→P

### Agent policy

- heuristic
- MLP
- prompt-only LLM
- SFT LLM
- oracle

### 机制消融

- feedback
- frozen-feedback
- same-evidence refinement
- strong one-shot

核心需要证明：

\[
Adaptive > Frozen
\]

说明真实 plan revision 有价值；

以及尽可能：

\[
Adaptive > Strong\ OneShot
\]

说明序贯反馈而非单纯更大资源产生额外价值。

---

# 十九、研究点二：安全扩展

研究点一默认：

\[
peer=benign
\]

研究点二扩展：

\[
peer\ may\ be\ compromised
\]

重点不是重新设计密码协议，而研究：

> 合法身份车辆返回“认证正确但语义错误”的 P/F evidence 时，Agent 如何避免错误协作。

攻击对象包括：

### P

- state shift；
- velocity/history distortion；
- stale/replay；
- selective omission；
- ghost target。

### F

- trajectory shift；
- mode suppression；
- probability manipulation；
- fabricated safe behavior；
- planning-targeted forecast manipulation。

---

# 二十、安全 Agent Loop

Tool result 原生保留：

- provider identity；
- timestamp；
- receipt；
- field identity；
- producer/model version；
- context version；
- confidence；
- parent refs。

研究点二加入：

\[
Trust(E)=
f(
provenance,
freshness,
temporal\ consistency,
cross-view\ consistency,
kinematic\ plausibility
)
\]

然后 Agent 可以进一步执行：

```text
ACCEPT
REJECT
P re-query
F re-query
FALLBACK
STOP
```

因此两个研究点形成：

\[
\boxed{
研究点一：如何有效调用远端能力
}
\]

\[
\boxed{
研究点二：如何安全地相信和使用远端能力
}
\]

# 二十一、当前建议的硕士论文总体题目

推荐：

**面向可信 V2X 协同驾驶的大模型远端能力调用与安全决策方法研究**

或更稳妥：

**面向车联网协同驾驶的任务驱动远端能力调用与可信决策方法研究**

---

# 二十二、近期实施顺序

当前不要直接开始微调大模型。

建议严格按以下顺序推进：

1. **确定/复现可靠 PLAN backbone。**
2. **冻结 Agent state 与 LLM visibility whitelist。**
3. **固定 P/F/current/change/STOP action contract。**
4. **建立离线 counterfactual Tool-label generator。**
5. **先运行 oracle policy feasibility study。**
6. 检查 P/F/STOP 和第二调用样本是否具有足够分布。
7. 构建 ToolV2X-Agent / Instruct 数据集。
8. 先做 heuristic / MLP / prompt-only LLM。
9. 再进行 SFT LLM。
10. 冻结 planner 后进行 feedback / frozen / one-shot 正式机制实验。
11. 研究点一稳定后，进入恶意 P/F 与可信调用研究。

## 最关键的阶段 Gate

在任何 LLM 大规模训练之前，必须先回答：

> **Oracle Tool policy 在公平预算下是否明显优于固定通信策略？**

若答案为否，应先修改任务/P/F/规划基础，而不是继续扩大 LLM 训练。

若答案为是，则：

> **训练 LLM 去逼近这个可证明有价值的调用策略。**

这将成为研究点一最稳固的实验逻辑。
