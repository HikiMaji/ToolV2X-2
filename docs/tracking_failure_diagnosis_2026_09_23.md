# S2失败原因分析与分层修复建议

2026-09-23。仅复核已有S2的151个状态/150次控制、冻结源码和官方0.9.15实现；未改运行器/PID/参考/判据，未启动CARLA、规划器或训练。离线脚本与证据见 [diagnosis.json](evidence/tracking_failure_diagnosis_2026_09_23/diagnosis.json) 和 [分析脚本](evidence/tracking_failure_diagnosis_2026_09_23/analyze_saved_s2.py)。

## 1. 结论和优先级

问题不只在一个PID增益。已发现四层问题：

1. **命令执行/读回时序未满足逐tick已确认假设。** 必须先补同步提交屏障和命令回显绑定，才能校准控制器。
2. **横向参考退化。** 停车阶段时间前视点与车辆原点几乎重合，原PID把微小定位误差解释成约77度的目标方向；这属于参考消费接口问题。
3. **纵向环的语义与定时轨迹要求不完整匹配。** 原环只看速度，不直接纠正沿程位置或停车位置；参考速度归零时，落后2.1m也会停。
4. **动态响应存在明显振荡与饱和。** 单位正确，控制计算可复现；增益、执行延迟、油门/制动力映射等影响尚未通过干预分离，不能直接认定改Kp即可解决。

另有float32边界误报，属于审计表示问题；不改变真实性能FAIL。当前不更换RP或新增模型，先把控制执行契约弄清楚。

## 2. 新发现：命令读回错位

将每行control_i与下一行last_control_(i+1)对齐，只比较throttle/brake/steer：

- 逐值完全相等检查有8处不一致。
- 容差1e-6时仍有7处：观察索引8、9、21、47、57、93、95；它们可匹配再前一行的命令。
- 容差放至1e-5仍有6处；所以不是仅由float32的末位误差造成。
- 一个明显例子：t=5.6s发出brake≈0.206875，t=5.7s记录的生效控制却为throttle≈0.469728（对应t=5.5s命令）。这里车辆的物理时钟仍连续，dt误差最大约1.49e-9s。

官方客户端的ApplyControlToVehicle走AsyncCall，不等待响应；GetControl读取最近快照中的control。故本地“actor.apply_control后紧接world.tick”不等于已经用同步屏障确认控制接收。异步提交与tick之间的排序是有源码依据的优先怀疑；尚不能凭读回精确反推每个物理子步的切换时刻，也不能说七条解释了全部轨迹误差。

来源：[Client.cpp](https://github.com/carla-simulator/carla/blob/0.9.15/LibCarla/source/carla/client/detail/Client.cpp)、[Vehicle.cpp](https://github.com/carla-simulator/carla/blob/0.9.15/LibCarla/source/carla/client/Vehicle.cpp)。

**建议修复A：** 每次控制使用 `client.apply_batch_sync([carla.command.ApplyVehicleControl(actor.id, control)], False)`，检查每个response无error后，才调用唯一一次world.tick；随后绑定预期frame与实测frame、命令与读回。False明确表示该batch不推进时钟，不能用True后再额外tick。初始化/几何准备也通过同一提交入口，保持20/1/9和全部控制值不变。RPC失败则当前命令未获确认，不继续下一物理步；读回不符记执行契约失败，不隐去或追溯改时间。

服务器apply_batch逐个执行命令并返回结果，只有显式do_tick_cue时才额外触发tick；这是提出该修复的依据，不是本机新路径已通过的证明。[CarlaServer.cpp](https://github.com/carla-simulator/carla/blob/0.9.15/Unreal/CarlaUE4/Plugins/Carla/Source/Carla/Server/CarlaServer.cpp)

## 3. 横向根因：把停车点当作方向指引

t=0的目标与actor距离0.000093248m，RH方向误差约−76.877度。由于纵横两个小偏差的比值不小，向量归一化消除了误差本来只有0.09mm这一尺度。0–1s参考要求静止、朝向不变，转向指令却0.1逐步升到0.8。

不是坐标误差大到无法驾驶，而是“向车身原点附近的一个点追踪”的方向定义不适用于停车。原官方LocalPlanner使用空间waypoint队列并移除已靠近的点；其调用背景是路径跟随+巡航速度。我们直接拿固定时间前视点喂低层PID，遗漏了空间目标选择的语义。[官方LocalPlanner](https://github.com/carla-simulator/carla/blob/0.9.15/PythonAPI/carla/agents/navigation/local_planner.py)

**建议修复B：** 横向消费参考几何和朝向，选有正向空间间隔的路径目标，不能仅由t+0.4s取点。停车段/重复点段用已知参考姿态明确方向，不再用车身到几乎重合点的向量求角度。空间目标与纵向时间律分开：横向选择路径上的前向点不允许车辆提前通过冲突区，纵向仍按原绝对时标执行。末端若使用切向虚拟目标，它仅是控制方向提示，不延长规划轨迹、不增加进展、不进入P/F请求或评分。

不推荐无条件steer=0（转弯停车可能有合法参考曲率）、用参考时间前移让点自然拉开、将车辆位置吸附到轨迹上，或增加仅对S2生效的停车分支。具体空间前视、连续性和端点规则要在控制版本中一次性定义，不在跑完后挑选。

## 4. 纵向：计算无误，不代表控制结构合适

用保存的当前速度和target_speed重算原PID：150次输出全部在1e-6内匹配，最大差2.98e-8。m/s→km/h转换没有遗漏；最大垂直速度只有6.96e-6m/s，3D模长中的垂直分量不足以解释振荡；全过程读回gear=1，不是继续空挡。

5≤t<9s为2m/s匀速目标，40次控制有12次油门/刹车符号切换，13次油门达上限、4次制动达上限；原生速度约1.691–2.193m/s，沿程误差在这4s又增加0.386m。积分贡献峰值在此区间仅0.0273，不能简单归为积分饱和。

当前Kp按km/h误差工作，忽略小积分项时，约0.208m/s欠速就足以达到0.75油门上限，约0.083m/s超速就能达到0.3制动上限。这说明此增益与当前低速、0.1s周期和执行器存在较激进的响应关系；它不是单位转换bug，也不能在时序未确认前据此拟合唯一车辆模型。[原PID](https://github.com/carla-simulator/carla/blob/0.9.15/PythonAPI/carla/agents/navigation/controller.py)

**位置反馈缺失是可直接确认的结构事实。** 原纵向输出只依赖目标/当前速度及最近速度误差。两个车拥有同样速度和误差历史，但一个位于目标位置、另一个落后2m，得到完全相同的油门/刹车。S2末段目标速度为0，实际停在13.9025m，参考终点16m；速度回零不会自动修复这2.0975m位置差。

**建议修复C：** 若继续要求按时间到达和准确停车，使用通用的纵向轨迹跟踪结构：参考速度/加速度 + 沿程位置和有符号速度误差反馈 + 终点剩余距离/停止约束。它应对所有场景和Ego/P/F一致，不是给S2补固定油门。参考加速度单位是m/s²，不能直接作为归一化油门/刹车；需要明确并验证执行器映射或复用合适的成熟跟踪器。控制与模型误差纳入规划执行余量。

可选的概念外环是以沿程误差修正速度目标，并受限速、制动距离与原计划约束限制；具体增益、前馈映射和边界还未验证，不在本稿捏造数值。禁止以“追上参考”为由取消冲突约束或恢复条件。若不愿承担这项适配，只能正式把接口降为路径+速度跟随并重新论证未来碰撞时序，不能保留定时轨迹主张却悄悄放宽位置门槛。

## 5. 数值审计修正单列

brake上限0.3和steer上限0.8经float32表达略大于十进制常量；原1e-12比较导致illegal_control/steer_slew误报。新审计应按字段实际表示误差设置容差（如float32 ULP尺度），并有真超限反例。不改物理性能阈值，不把旧FAIL改成PASS；位置、速度、加速度等7项真实失败仍成立。

## 6. 推荐的修复/验证顺序

| 顺序 | 修改/核查范围 | 能回答的问题 | 不允许得出的结论 |
|---|---|---|---|
| A 执行时序 | 同步确认提交、单次tick、frame和control回显绑定；初始化控制值不变 | 下一物理步是否确实对应已确认命令；消除传输/读回错位解释 | 时序过关不等于跟踪已合格 |
| B 横向语义 | 有空间间隔的参考方向；静止/末端明确处理，纵向参数不动 | 静止微小误差是否仍造成方向发散，低速/曲线是否连续 | 横向修正不证明全部纵向误差由它导致 |
| C 纵向跟踪 | 在执行时序确定后，校准有界车辆响应，补位置/速度/终点反馈或选择成熟跟踪器 | 满足给定参考的时标、停止点和动态门槛 | 参数校准集的结果不能充当独立通过 |
| D 共用门槛 | 修订版本冻结后再跑原分层独立参考验证 | 限定任务域内共同控制可用 | 不等于RP、真实感知、F质量或ToolV2X收益通过 |

优先实施A。它是记录与实际执行关联的前置条件，改动小且有明确源码依据，不需重新选型。A/B/C应分开版本或明确差异，不一次同时改完后把结果归给某一个原因。后续若需要改控制器或校准，先明确工作量上限、校准/验收分离和退出条件，不恢复无限调参。

本轮只新增分析脚本、逐步PID重算证据和本报告，更新STATUS入口；没有运行任何候选修复。原S2失败、原始时间戳及全部旧判定保持不变。
